# Архитектура

Проект устроен как модульный монолит.

HTTP API и Telegram-бот являются адаптерами. Они разбирают внешний ввод, определяют прикладного `Actor` и вызывают application use cases.

Валидация API-запросов реализована через Zod в `src/api/schemas.ts`. Типы body и params на уровне контроллеров выводятся из тех же схем через `z.infer`, поэтому runtime-валидация и TypeScript-типы используют один источник правды.

Application use cases владеют бизнес-операциями и границами транзакций БД. Мутации карт выполняются внутри `db.transaction(...)`; debit и credit блокируют строку карты перед расчётом нового баланса.

Правила авторизации находятся в `src/application/card-access-policy.ts`. Адаптеры определяют идентичность, но решения о доступе к ресурсу выражаются как проверки actor/action/resource в application-слое. Это не даёт глобальным правам оператора и проверкам владения ресурсом расползаться по Telegram и HTTP handler-ам. Слой описан в `docs/access-control-ru.md`.

Репозитории владеют Knex-запросами и не принимают бизнес-решения.

Ограничения БД защищают критичные инварианты балансов, сумм транзакций и внешних ключей.

Деньги в application-коде пока представлены JavaScript `number`. Текущая архитектура защищает базовые инварианты сумм через Zod, проверки use case-ов и ограничения БД; отдельный money value object остаётся возможным будущим улучшением.

## Принятый дизайн: подтверждение операций чеками

`transactions` остается ledger-ом баланса карты. Подтверждения фискальными чеками хранятся отдельно в `transaction_receipts` и связываются с конкретной операцией `CREATE`, `DEBIT` или `CREDIT`.

В мягком режиме операторская операция сначала применяется к карте, затем бот просит отсканировать QR фискального чека или указать причину пропуска. Статусы чеков: `pending_verification`, `verified`, `failed`, `skipped`. При `failed` автоматическая корректировка баланса не выполняется; случай разбирается операционно.

Ссылка на чек не считается источником истины. Система хранит исходный QR payload и нормализованные фискальные поля, а ссылку для браузера строит из этих данных, когда это возможно.

История владельца карты показывает статусы и ссылки на чеки для `DEBIT` и `CREDIT`. Причины пропуска и комментарии видят только оператор или администратор. Чек `CREATE` подарочной карты хранится для аудита, но не показывается владельцу, потому что карта может быть куплена одним человеком и подарена другому.

## Принятый дизайн: владение картами клиентами

Подарочные карты сохраняют текущее разделение между внутренним `cards.id` и публичным `cards.code`. Публичный код остаётся QR/manual-entry идентификатором для операторских сценариев. QR-изображения, которые генерирует бот, кодируют ровно plain text `cards.code`; они создаются по запросу через `qrcode` и не хранятся в БД.

Модель владения добавляет provider-neutral клиентов:

- `customers` хранит внутренние записи клиентов.
- `customer_identities` связывает клиентов с внешними аккаунтами через `provider` и `provider_user_id`; Telegram сейчас является только первым провайдером.
- `card_owners` хранит текущего владельца карты. Текущая продуктовая модель допускает одного владельца на карту и одну текущую карту на клиента.
- `card_transfer_tokens` и `card_owner_transfers` поддерживают передачи, инициированные владельцем, и audit history.

Application use cases должны работать с `customer.id`. Telegram-специфичные данные должны оставаться в bot adapter и на границе identity repository.

Для аккаунтов с привязанной картой персональные действия бота используют эту карту по умолчанию: balance, history, my card, unlink, transfer и link status. Операторские cash-register действия, такие как debit и credit, по-прежнему требуют явный QR scan или публичный код. Public balance lookup остаётся bearer-style, но история owned card доступна только владельцу или оператору.

Подробный принятый дизайн задокументирован в `docs/superpowers/specs/2026-06-25-card-ownership-transfer-design.md`.

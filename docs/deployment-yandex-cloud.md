# Yandex Cloud Deployment

Production runs the API as a Yandex Serverless Container and the Telegram bot as a long-polling container on a Yandex Compute Cloud VM created with Container Solution. Release images are stored in Yandex Container Registry, PostgreSQL runs in Yandex Managed Service for PostgreSQL, and application secrets are stored in Yandex Lockbox.

This document reflects the current `.github/workflows/release-polling-vm.yml`. The old webhook workflow remains in `.github/workflows/release.yml`, but it is disabled for automatic tag releases and can only be started manually with `workflow_dispatch`.

## Current Release Architecture

The release workflow:

- starts on tags matching `v*.*.*`;
- requests a GitHub OIDC token with `permissions.id-token: write`;
- exchanges that token for a short-lived Yandex Cloud IAM token through `yc-actions/yc-iam-token-fed`;
- installs and configures the Yandex Cloud CLI;
- reads release secrets from Lockbox into masked GitHub Actions environment values;
- logs in to Yandex Container Registry;
- builds and pushes API, bot polling, and migrations images;
- runs migrations from the GitHub Actions runner using the migrations image;
- deploys the API Serverless Container revision;
- creates or updates the Compute Cloud VM that runs the long-polling bot container;
- deletes the Telegram webhook so `getUpdates`/long polling can receive updates.

Important network constraint: migrations currently run from a GitHub-hosted runner. For the first deployment, Managed PostgreSQL must be reachable from GitHub Actions, for example through a public endpoint. A stricter production setup should run migrations inside Yandex Cloud/VPC and add `revision-network-id` to the Serverless Container deployments.

## Infrastructure

Required Yandex Cloud resources:

- VPC network and subnet.
- Managed PostgreSQL database.
- Container Registry.
- Lockbox secret with runtime configuration keys.
- Workload Identity Federation for GitHub Actions.
- CI service account for GitHub Actions deployments.
- Runtime service account for Serverless Container revisions.
- API Serverless Container.
- Compute Cloud VM for the long-polling bot.

Use the VPC `network-id` that owns the PostgreSQL subnet. If the subnet is not in a network named `default`, using `--network-name default` during PostgreSQL creation can fail with `subnet "<subnet_id>" not found`; use `--network-id` instead.

The CI service account must be able to exchange the GitHub OIDC token for a Yandex Cloud IAM token, read Lockbox payloads for release steps, resolve Lockbox secret metadata during `revision-secrets` deployment, push Container Registry images, use the VPC network, deploy Serverless Container revisions, and recreate the Compute VM that runs the bot. The runtime service account must be able to pull images, read Lockbox payloads, and use the VPC network.

## Runtime Configuration

Lockbox secret keys:

```text
DB_HOST
DB_PORT
DB_NAME
DB_USER
DB_PASSWORD
TELEGRAM_BOT_TOKEN
TELEGRAM_WEBHOOK_SECRET
WEB_APP_URL
```

`TELEGRAM_WEBHOOK_SECRET` is only required by the old webhook workflow. It is generated by us, not by Telegram or Yandex Cloud:

```bash
openssl rand -hex 32
```

The same value must be stored in Lockbox and used when Telegram webhook is registered. The current workflow reads it from Lockbox and passes it to Telegram `setWebhook`.

The API container receives:

```text
API_HOST=0.0.0.0
DB_SSL=true
DB_POOL_MIN=0
DB_POOL_MAX=2
```

The bot polling VM container receives:

```text
TELEGRAM_MODE=polling
DB_SSL=true
DB_POOL_MIN=0
DB_POOL_MAX=2
```

The API revision is attached to the VPC network identified by `YC_NETWORK_ID` so it can reach Managed PostgreSQL through the cloud network. The bot VM is attached to `YC_SUBNET_ID` and receives a public NAT address for outbound Telegram API access; it does not need inbound public access for polling.

The bot VM does not receive DB or Telegram secrets through Compute metadata. The workflow writes only `user-data` with the image tag and Lockbox secret id. On boot, a systemd unit reads Lockbox through the VM service account, writes a root-only env file, logs in to Container Registry with the VM IAM token, and starts the polling container with `docker run --restart always`.

Yandex Serverless Containers supplies `PORT`; do not set `API_PORT` in production.

The API Serverless Container must have `serverless.containers.invoker` granted to unauthenticated users. This is configured once on the container resource, not during every revision deploy, so the CI service account does not need access-binding administration permissions. The polling bot VM does not need a public HTTP endpoint.

## GitHub Secrets

No GitHub secrets are required by the current workflow when federation is configured correctly.

Do not add long-lived `YC_SA_JSON_CREDENTIALS` for this workflow. The workflow uses GitHub OIDC and short-lived Yandex Cloud IAM tokens instead.

## Yandex Cloud Authentication

The workflow must have:

```yaml
permissions:
  contents: read
  id-token: write
```

It obtains an IAM token through:

```yaml
- name: Get Yandex Cloud IAM token
  id: iam-token
  uses: docker://ghcr.io/yc-actions/yc-iam-token-fed:1.0.0
  with:
    yc-sa-id: ${{ vars.YC_CI_SA_ID }}
```

Yandex Cloud actions receive this token through `yc-iam-token`:

```yaml
- name: Login to Yandex Cloud Container Registry
  uses: yc-actions/yc-cr-login@v3
  with:
    yc-iam-token: ${{ steps.iam-token.outputs.token }}
```

Yandex Cloud CLI commands receive the same IAM token through `YC_IAM_TOKEN`:

```yaml
- name: Read release secrets from Lockbox
  env:
    YC_IAM_TOKEN: ${{ steps.iam-token.outputs.token }}
    YC_LOCKBOX_SECRET_ID: ${{ vars.YC_LOCKBOX_SECRET_ID }}
  run: yc lockbox payload get --id "$YC_LOCKBOX_SECRET_ID" --key DB_HOST
```

Do not pass this IAM token to `yc config set token`; that config property is for an OAuth token and causes the CLI to try creating a new IAM token from an invalid OAuth value.

Configure Yandex Cloud Workload Identity Federation so only this GitHub repository, and ideally only release tag refs, can impersonate the CI service account.

## Release Secrets Read From Lockbox

The release workflow reads the values needed by migrations and the polling bot:

```text
DB_HOST
DB_PORT
DB_NAME
DB_USER
DB_PASSWORD
TELEGRAM_BOT_TOKEN
WEB_APP_URL
```

The workflow masks each value and writes it to `$GITHUB_ENV` for later steps. The API revision receives database secrets through `revision-secrets`; the VM reads its runtime secrets directly from Lockbox during boot.

## Release Flow

Create and push a version tag:

```bash
git tag v1.2.3
git push origin v1.2.3
```

GitHub Actions then:

1. Runs `npm ci`, `npm run typecheck`, and `npm test`.
2. Exchanges the GitHub OIDC token for a short-lived Yandex Cloud IAM token.
3. Installs and configures the Yandex Cloud CLI.
4. Reads release secrets from Lockbox.
5. Logs in to Yandex Container Registry.
6. Builds and pushes `ion-gift-card-api`, `ion-gift-card-bot-polling`, and `ion-gift-card-migrations` images tagged with the Git tag.
7. Runs the migrations image before deploying runtime revisions.
8. Deploys the API Serverless Container revision with Lockbox-backed secrets and `YC_NETWORK_ID`.
9. Recreates the Compute VM for the long-polling bot. The bot is stateless; durable state stays in PostgreSQL.
10. Calls Telegram `deleteWebhook` with `drop_pending_updates=false`.

If checks, image push, migrations, deployment, VM update, or Telegram webhook deletion fail, the workflow stops before later release steps. Rollback is done by redeploying a previous image tag as a new Serverless Container revision for the API and updating the bot VM container to a previous image tag; database rollback is not automatic.

## Post-Deploy Checks

Check health endpoints:

```bash
curl https://<api_container_url>/health
```

Check that the old Telegram webhook is removed if the bot was previously deployed in webhook mode:

```bash
curl "https://api.telegram.org/bot<token>/getWebhookInfo"
```

Then send `/start` to the bot in Telegram.

## Hardening After First Deployment

- Close public PostgreSQL access after confirming runtime VPC access works.
- Move migrations into Yandex Cloud/VPC so GitHub runners do not connect to the database directly.
- Restrict federation conditions to this repository and release tag refs.
- Pin third-party actions/images by digest where supply-chain risk matters.

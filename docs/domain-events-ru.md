# Доменные события и ledger карты

Этот документ фиксирует принятое направление для расширения приложения акциями, бонусной системой, публикацией новостей, розыгрышами и похожими продуктовыми механиками.

## Решение

Оставить `transactions` узким ledger-ом карты.

Отдельный поток доменных событий добавить тогда, когда первая кросс-доменная функция потребует бизнес-факты за пределами баланса карты.

## Транзакции карты

`transactions` нужны, чтобы объяснять `cards.balance`.

Они должны отвечать на вопросы:

- Почему у карты сейчас такой баланс?
- Можно ли пересчитать баланс по ledger-у?
- Было ли случайно задублировано списание или пополнение?
- Какая корректировка нужна, если операцию по карте внесли ошибочно?

`transactions` должны оставаться сфокусированными на операциях, которые меняют баланс карты: создание карты, списание, пополнение и будущие явные корректировки баланса карты.

`transactions` не должны становиться общим аудит-логом для акций, бонусов, новостей, розыгрышей и других продуктовых процессов.

## Доменные события

Доменные события фиксируют бизнес-факты.

Примеры:

- `card.created`
- `card.debited`
- `card.credited`
- `customer.card_linked`
- `promotion.reward_granted`
- `loyalty.points_earned`
- `raffle.entry_created`
- `news.published`

События нужны для двух целей:

- Аудит и аналитика: увидеть, что происходило в бизнесе.
- Реактивная обработка: дать будущим модулям возможность реагировать на факты без прямой связки с карточными use case-ами.

## Форма события

Будущая таблица `domain_events` должна быть append-only и должна указывать основной aggregate, которому принадлежит факт.

Рекомендуемая форма:

```text
domain_events
- id
- event_type
- aggregate_type
- aggregate_id
- actor_type
- actor_id
- customer_id nullable
- card_id nullable
- operator_id nullable
- promotion_id nullable
- raffle_id nullable
- metadata jsonb
- occurred_at
```

`aggregate_type` и `aggregate_id` являются основными полями принадлежности. Денормализованные ссылки вроде `customer_id` и `card_id` нужны для поиска, поддержки, отчетов и обработчиков будущих функций.

Пример после списания с карты:

```text
transactions
  card_id=123
  type=DEBIT
  amount=500
  balance_after=1500

domain_events
  event_type=card.debited
  aggregate_type=card
  aggregate_id=123
  card_id=123
  customer_id=456
  actor_type=operator
  actor_id=789
  metadata={ amount: 500, transaction_id: "..." }
```

## Реактивная обработка

Реактивные модули не должны вызываться напрямую из `CardUseCases`.

Когда функции понадобится надежная реакция на событие, нужно добавить outbox или таблицу доставок:

```text
event_deliveries
- id
- event_id
- handler
- status
- attempts
- last_error
- processed_at nullable
- created_at
```

Это позволит повторять или переигрывать работу конкретных модулей без изменения ledger-а карты.

Примеры обработчиков:

- `loyalty.on_card_debited`
- `raffles.on_card_debited`
- `notifications.on_news_published`

Первая реализация доменных событий может быть синхронной и простой: событие записывается в той же транзакции БД, что и исходный use case. Асинхронные повторы стоит добавлять только тогда, когда они понадобятся реальной функции.

## Границы

Карточные use case-ы могут публиковать факты об операциях с картой. Они не должны знать, какие акции, бонусные правила, розыгрыши или уведомления эти факты используют.

Акции, бонусы, новости и розыгрыши должны владеть своими таблицами и ledger-ами. Они могут ссылаться на `domain_events`, `customers` и `cards`, но не должны хранить свое состояние в `transactions`.
